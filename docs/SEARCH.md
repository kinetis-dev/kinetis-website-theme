# Site-wide search

kinetis.dev is built by three Sphinx projects that all render with this
theme: the website (`/`, with the blog under `/blog/`), the Kinetis docs
(`/docs/`) and the Vector docs (`/vector/docs/`). From 0.5.0 every search
box on every page searches all of them. This file is the contract the
theme and the three consumers follow.

Pagefind's behaviour below was checked against Pagefind 1.5.2's
documentation and its shipped `pagefind.js` and `pagefind-component-ui.js`.
Re-check it whenever the pinned version changes.

## 1. Pagefind and its version

- Search is [Pagefind](https://pagefind.app/), **1.5.2**, the same version
  in every repository.
- Each consumer installs it from PyPI, so no Node is needed anywhere. Pin
  both packages exactly. The wrapper alone accepts any 1.x binary
  (`pagefind-bin-extended>=1,<2`), and bundles built by different binaries
  must not meet in one search (§4.4).

  ```
  pagefind[extended]==1.5.2
  pagefind-bin-extended==1.5.2
  ```

- Each consumer indexes its own finished build, after `sphinx-build` and
  after any step that removes files from the output, and before the
  build's checks:

  ```sh
  python -m pagefind --site <output-dir>
  ```

  No other flag and no `pagefind.yml`. The theme's markup (§2, §3) carries
  everything Pagefind needs. Pagefind exits non-zero only when it finds no
  HTML page at all. A build that lost its `data-pagefind-body` markers does
  not fail: Pagefind then indexes every page's whole `<body>`, 404 and
  listings included, and exits 0. The theme's tests pin the indexed page
  set, so a theme release cannot lose the markers unnoticed.
- The bundle lands at `<output-dir>/pagefind/` and is deployed with the
  build. The three bundles are:

  | Section | Bundle |
  |---|---|
  | Website and blog | `/pagefind/` |
  | Kinetis docs | `/docs/pagefind/` |
  | Vector docs | `/vector/docs/pagefind/` |

  The website's root sync must not delete the other two, which it does not
  touch already, since it excludes the reserved `/docs/` and `/vector/`
  prefixes.
- The UI is Pagefind's Component UI (`pagefind-component-ui.js` and `.css`),
  loaded from a bundle at runtime. The theme vendors no Pagefind file.

## 2. What is indexed

**Rule.** A page is indexed when it is a source document of the build (its
name is in `env.found_docs`) and it is not noindex by the theme's existing
rule (`is_noindex`: `404`, front matter `kinetis_noindex: true`, or a
`kinetis_noindex_patterns` match). Only an indexed page carries
`data-pagefind-body`. Once one page of a build carries it, Pagefind skips
every page without it, so this one rule decides the whole index. It must
be computed from the environment, not from per-page state, so `-j` builds
index the same pages.

What the rule gives:

| Page | Indexed | Why |
|---|---|---|
| Docs pages, blog posts, `blog/index` | yes | source documents |
| The website landing page `/` (`kinetis_template: landing`) | yes | It is the product overview, and "Kinetis" or "PHP framework" should find it. Its body is the `.kinetis-landing` element. |
| `404` (a landing page too) | no | always noindex |
| ablog listings (`blog`, `blog/tag*`, `blog/<year>`, …) | no | generated, not source documents; the website also marks them noindex |
| `search`, `genindex`, `py-modindex` | no | generated by Sphinx |
| Any page marked `kinetis_noindex: true` or matching a pattern | no | noindex |

**Indexed region.** It is the article on docs pages (`article.bd-article`)
and `.kinetis-landing` on landing pages, as now. The header, both sidebars
and the footer stay outside it; the theme already marks them
`data-pagefind-ignore`, and Pagefind skips `<nav>`, `<footer>`, `<script>`
and `<form>` itself.

**Permalink icons.** Sphinx ends every heading with
`<a class="headerlink">#</a>`. Unhandled, Pagefind takes the title
`Routing#` and indexes `params#`. The theme sets `html_permalinks_icon` to
`<span data-pagefind-ignore>#</span>`, which renders the same `#`. It does
so only when the consumer has not set the option (pydata's own test,
`config_provided_by_user`). pydata writes `"#"` in its `builder-inited`
handler at the default priority, so the theme's handler must run after it.

**Title.** Every indexed page carries
`<meta data-pagefind-meta="title[content]" content="…">` in its head. The
content is the page title with tags stripped, the same text as the first
part of `<title>` without the ` - Project` suffix. Docs pages then keep
their h1 text. Landing pages get their `{title}` directive text rather than
the first `<h1>` of the raw body.

**Sub-results** (one result per matching heading) are off (§5).
Pagefind splits pages on headings that have an `id`, but docutils puts the
ids on the enclosing `<section>`, so Sphinx output yields none.

## 3. Sections

Every indexed page carries one filter and one meta value, both named
`section`, set inline on its `data-pagefind-body` element:

```html
<article class="bd-article" data-pagefind-body
         data-pagefind-filter="section:Docs" data-pagefind-meta="section:Docs">
```

The value comes from the theme's own `active_section()` on the page's
deployed path, mapped as follows:

| `active_section` | `section` |
|---|---|
| `Docs` | `Docs` |
| `Vector` | `Vector` |
| `Blog` | `Blog` |
| `Home`, or no item | `Main` |

The deployed path comes from `html_baseurl`, as for the navbar. All three
consumers set it, and it is required for correct sections. Blog is decided
per page because the website's one bundle holds both Main and Blog pages,
so a per-bundle `mergeFilter` could not tell them apart. All bundles keep
`indexWeight` 1, so no section is weighted.

## 4. Bundles in the browser

### 4.1 Candidates

The theme knows the three bundle paths as a constant, next to `NAV`:

```python
SEARCH_BUNDLES = ("/pagefind/", "/docs/pagefind/", "/vector/docs/pagefind/")
```

There is no configuration value: consumers set nothing.

In the browser the candidate list is:

1. the page's **own** bundle: `pagefind/` resolved against the page's
   content root (`<html data-content_root>`, which pydata stamps);
2. then the three `SEARCH_BUNDLES`, in order, as root-relative paths;

with duplicates removed after resolution. Deployed, the own bundle equals
one of the three. In a local preview of one build served at `/`, the own
bundle resolves to `/pagefind/` and the docs prefixes simply do not exist.

### 4.2 Probing

Pagefind 1.5.2 has no tolerance for a missing bundle. The Component UI
merges indexes in a loop with no error handling, and a merged bundle whose
`pagefind-entry.json` fails to load throws, so the whole instance never
finishes loading. The theme therefore probes before it configures anything:

- It sends one `GET <bundle>pagefind-entry.json` per candidate, in
  parallel, with `cache: "no-store"`, when the page loads.
- A bundle is **present** when the response is OK and parses as JSON with a
  string `version` and an object `languages`. Anything else means absent: a
  404, the website's HTML 404 page, a network error, or `file://`.

### 4.3 Configuring

- **Primary** is the own bundle if it is present, otherwise the first
  present candidate in order. The theme loads `pagefind-component-ui.css`
  and `pagefind-component-ui.js` from the primary, then calls
  `configureInstance` with `bundlePath` set to the primary and `mergeIndex`
  set to every other present bundle. Only after that does it insert the
  `<pagefind-*>` elements. `configureInstance` is ignored, with only a
  `console.warn`, once a component of the same instance has connected, so
  no `<pagefind-*>` element is in the static HTML.
- **Result URLs** need no option. Pagefind derives each bundle's base URL
  from its path (`/docs/pagefind/` gives `/docs/`), so links from every
  bundle are correct on every section.
- **No bundle present** means no search UI is inserted, and the navbar slot
  stays empty. Nothing throws, and nothing is logged above `console.warn`.

### 4.4 Version skew

A present bundle whose `version` differs from the primary's is not merged;
the theme logs one `console.warn` for it. Merged indexes are searched with
the primary's WebAssembly, so a skewed bundle could fail at query time. The
pins in §1 keep the three bundles on one version, so skew only happens
mid-rollout.

### 4.5 What each situation gives

| Situation | Result |
|---|---|
| Deployed, all three bundles live | Every page searches all four blocks. |
| First rollout, one docs bundle not yet deployed | That section's own pages are missing from results; everything else works. |
| Local preview of one build (`python -m http.server -d <out>` after indexing, or `python -m pagefind --site <out> --serve`) | Results from that build only, with links that work locally. |
| Theme tests' sample builds without indexing, or `file://` | No search UI. |

## 5. UI

- **Trigger and modal.** `navbar_persistent` defaults to
  `["kinetis-search"]`, a new component, instead of pydata's
  `search-button`. Its static markup is an empty placeholder;
  `kinetis-search.js` fills it as in §4.3. pydata renders every
  `navbar_persistent` item twice, for wide and narrow screens, and hides one
  copy with `display: none`, under which a `<dialog>` never shows. So each
  placeholder gets its own trigger and the one modal goes in `<body>`:
  - a `<pagefind-modal-trigger>` in each placeholder;
  - one `<pagefind-modal>` whose contents are, in order:
    - `<pagefind-input>`;
    - a `<pagefind-filter-dropdown filter="section" label="Section">`;
    - `<pagefind-summary>`;
    - `<pagefind-results hide-sub-results>`;
    - `<pagefind-keyboard-hints>`.

  The results template shows the title link, the section as a small label,
  and the excerpt. On narrow screens the trigger must fit pydata's header
  without wrapping, compact (icon only) if needed.
- **pydata's search is turned off.** `disable_search` defaults to `True`,
  which removes `#pst-search-dialog`. Merged key by key as today, a consumer
  can still override either default.
- **No Sphinx search assets on ordinary pages.** pydata's `extrahead` loads
  `_static/searchtools.js`, `_static/language_data.js` and `searchindex.js`
  on every page. On the Kinetis docs, `searchindex.js` is the whole Sphinx
  index. The theme's `extrahead` stops loading these three. It must still
  emit everything else pydata's block does (viewport, `color-scheme`, the
  `docsearch:*` metas and `docbuild:last-update`), then the favicons and the
  noindex meta as now. This is a copy of a block of the pinned pydata
  0.23.0, so a test pins its output.
- **Shortcut.** Ctrl+K, or ⌘K on macOS, opens the modal: Pagefind's default
  `mod+k`. Escape closes it and focus returns to the trigger. pydata's own
  listener stays registered and calls `preventDefault()`, but with no search
  dialog it does nothing else. Pagefind's listener does not check
  `defaultPrevented`, so the two coexist; a test must prove the modal opens
  exactly once. One difference from pydata: Pagefind ignores the shortcut
  while focus is in an input, a textarea or contenteditable.
- **`search.html` stays**, at the same URL, with the same `<title>`
  (`Search - Project`). Both docs baselines list it, and its baselined
  anchor `search-results` stays inside the main landmark. The theme
  overrides pydata's `search.html`. The page keeps its `<h1>` "Search" and
  holds a full-page search on a separate Pagefind instance (`page`),
  configured the same way:
  - `<pagefind-input>`, prefilled and searched from `?q=`;
  - the `section` filter;
  - `<pagefind-summary>`;
  - `<pagefind-results>`.

  It sits inside an element with `id="search-results"` and has a
  `<noscript>` note. The modal works there too. The page is never indexed
  (§2), and the website keeps it noindex with its existing `search`
  pattern.
- **`searchindex.js` stays.** Sphinx still writes it and both docs
  baselines list it, but nothing loads it any more. Removing it is a later,
  separate URL decision.
- **Colours.** The theme sets the Component UI's `--pf-*` variables from
  pydata's tokens, so the modal follows `html[data-theme]` in light and
  dark mode. CSS custom properties pass through the components'
  `all: initial`. Never use `prefers-color-scheme` or `data-pf-theme`.
  - **Focus is Kinetis red `#DC2626` in both modes**: `--pf-outline-focus`
    and `--pf-border-focus`, and any `.bd-search` input pydata might still
    render (`:focus`, `:focus-visible`, `:focus-within`). Today the pink
    focus is pydata's `--pst-color-accent`. Define the red once as a theme
    variable (`--kinetis-red`), and use that variable for `.bd-article h1`
    too.

## 6. Non-goals for 0.5.0

- Sub-results per heading (§2).
- Weighting between sections, or a section preference per page.
- Cross-origin bundles or CORS: everything is on kinetis.dev.
- Removing `search.html` or `searchindex.js`.
- Search analytics or query logging.
- A configuration value for the bundle list.
- The blog-only results of today's search on the blog. That was Sphinx
  search behaviour, and it goes away with it.

## 7. Consumer duties (0.5.0)

All three consumers:

- bump the pin to 0.5.0, with `tools/bump_pin.py`;
- add the two Pagefind pins from §1 to the requirements file that builds
  the docs or site;
- run `python -m pagefind --site <output-dir>` in CI and in the deploy
  workflow, right after the build and its file removals, and before the
  checks;
- let their URL guards accept the new `pagefind/` files (new URLs are
  allowed by the docs baseline rules);
- keep `html_baseurl` set to the deployed URL.

Order:

1. Release the theme.
2. Deploy kinetis and vector-dev, in either order.
3. Deploy the website last, then confirm that a search from each block
   returns results from all four.

Until a section deploys, the other sections search without it (§4.5).
